DESIGN PATTERN: Strategy Pattern
MODULE: Payment & Transaction Management

PROBLEM
Before this change, PaymentService handled payment-method-specific behavior directly.
The create payment flow contained conditional checks for method-specific fields:

- BANK_TRANSFER required a bank reference.
- CHEQUE required a cheque number.
- CASH and DEMO_CARD_GATEWAY did not require extra method details.
- New payments were initialized as PENDING inside PaymentService.

This made PaymentService responsible for both common payment rules and individual
payment method behavior. If a new payment method is added later, PaymentService
would need more conditional logic.

SOLUTION
The Strategy Design Pattern was introduced for payment method behavior.

PaymentService now handles common payment workflow rules:

- customer/booking ownership checks
- approved booking validation
- reserved land validation
- amount validation
- remaining balance validation
- transaction reference generation
- persistence
- payment completion flow
- pessimistic locking for write/update operations

Each payment method now has its own strategy class for method-specific validation
and initialization.

PAYMENTSERVICE CHANGES

PaymentService now receives PaymentStrategyFactory through constructor injection:
- src/main/java/com/landhub/payment/PaymentService.java:29-38

In createCustomerPayment, PaymentService:

1. Finds the customer's booking.
2. Applies common payment validation.
3. Resolves the selected PaymentMethod.
4. Builds the Payment entity.
5. Gets the matching PaymentStrategy from PaymentStrategyFactory.
6. Calls strategy.validate(payment).
7. Calls strategy.initialize(payment).
8. Saves the payment.

BUSINESS RULES PRESERVED

The Strategy Pattern change does not remove existing common payment rules:

- Only the payment owner can create/view customer payments through the existing
  controller/service flow.
- Payments still require an approved booking.
- The booking land must still be reserved for payment.
- Payment amount must be greater than zero.
- Payment amount cannot exceed the remaining booking balance.
- Failed payments are not counted as paid because summaries still count only
  PaymentStatus.PAID.
- Booking completion after full payment is still handled after markPaid.
- Transaction references are still generated by PaymentService.

CONCURRENCY PROTECTION PRESERVED

The Strategy Pattern change does not remove pessimistic locking from payment
write/update operations.

PaymentService still uses the existing booking update path before marking a
payment as paid:

- src/main/java/com/landhub/payment/PaymentService.java:180-195

This keeps locking for payment processing and booking completion behavior outside
the strategy classes, where it belongs.

WHY STRATEGY PATTERN WAS CHOSEN

Strategy was chosen because payment method behavior varies by payment method,
while the overall payment creation workflow stays the same.

The pattern allows each payment method to define its own validation and
initialization without growing PaymentService with more if/else blocks.

BENEFITS

- Cleaner PaymentService.
- Method-specific rules are isolated in separate classes.
- New payment methods can be added by creating another PaymentStrategy.
- Existing common payment validation stays centralized.
- Existing payment workflow and security behavior are preserved.
- The design is easier to explain for a university assignment because each
  payment method is a concrete strategy.

VIVA EXPLANATION

In the Payment module, I used the Strategy Design Pattern to separate different
payment method behaviors from the main PaymentService.

PaymentService is the context. It manages the common payment workflow, such as
checking the booking, validating the amount, generating a transaction reference,
and saving the payment.

PaymentStrategy is the interface. Each concrete strategy represents one payment
method. For example, BankTransferPaymentStrategy validates the bank reference,
ChequePaymentStrategy validates the cheque number, and CashPaymentStrategy and
DemoCardPaymentStrategy initialize normal pending payments without extra fields.

PaymentStrategyFactory chooses the correct strategy based on PaymentMethod.
This avoids method-specific if/else validation inside PaymentService. If a new
payment method is added later, I can add a new strategy class instead of changing
the main service logic.

The existing payment business rules and locking behavior remain in PaymentService
and BookingService because they are common workflow rules, not individual payment
method strategies.
